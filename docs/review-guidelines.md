# desk 工程 Review 规范

适用于 desk 的文档、缺陷修复、功能、契约、数据、AI、前端/小程序和部署改动。配合 [开发规范](../AGENTS.md)、[产品与技术基线](../README.md)、[阶段目标](stage-goals.md) 使用；[需求评审记录](requirements-review.md) 负责历史产品来源追踪，两者用途不同。

当前仓库处于文档基线阶段。评审必须区分“文档规定的行为”“代码已实现的行为”和“实际验证通过的行为”，不能因为没有尚未进入实现阶段的代码就阻塞合理的文档改动。

## 目标与适用原则

Review 应判断问题发生在哪个机制、修复是否落在拥有完整信息的责任层，以及验证是否覆盖真实影响范围。“最小改动”是恢复正确行为所需的最小完整改动，不是文件或行数最少。

本规范不固定类型、枚举、目录层数、helper 数量或代码行数。阻塞结论必须指出受破坏的行为约束、证据与实际后果；个人风格偏好及尚未采纳的工程建议不能当作确定缺陷。选择与改动有关的检查，不机械穷举全部领域。

## 七个通用 Review 机制

### 1. 先明确应当保证的行为

先区分现象与约束，再讨论实现。说明“在什么条件下，系统应该或不应该发生什么”，并定位到 README、阶段目标、已有接口语义或用户明确要求。

例如，“学生看到了答案”是症状；“进行中的正式考试，学生不能经检索、引用或工具获得未公开答案”才是需要验证的约束。新需求超出本期时指出范围变化，不能用不明确的期望补出隐含产品承诺。

### 2. 建立因果链，找到第一个错误决定

从真实入口追踪：

```text
网页/小程序/任务入口 → Go 授权与领域决定 → MySQL/事件/AI → 消费者 → 学生或外部系统效果
```

PR 中的根因是待验证假设，不能直接采信。检查同一入口、同一数据的其他消费者，以及持久化和刷新路径。若只在页面新增过滤条件，却仍允许 Go 发布未审核题，就没有修复正式使用的责任边界。

文档改动也要建立来源链：用户要求/原产品依据 → 当前定义 → 阶段与技术约束 → 验收。检查改名、拆分或迁移是否造成遗漏、断链和相互矛盾。

### 3. 确认责任层与事实来源

根据实际运行链路判断谁拥有完整信息，不先假定必须修改哪一层。desk 的既定边界是 Go 负责业务授权和写入、MySQL 保存权威记录、Python 返回建议；前端、模型文本、聊天记录、缓存与向量索引不能代替这些决定。

下游可以防御性校验并在无权限时拒绝，但不能各自猜测相同业务规则。尤其检查租户、学生、题目版本和成绩版本是否来自受信任上下文，而非模型或“最新一条记录”的反推。

### 4. 审计既有机制，再新增抽象

新增字段、状态、配置、重试或兜底前，搜索相邻模型和全部调用点，解释现有机制为何不足、新旧语义如何划分。可复用、扩展或替换，但不能为一个 case 另建平行权限、审核状态或成绩确认规则。

尚无实现的模块不要求虚构复用对象；先建立满足阶段目标的最小机制，并说明契约和扩展边界。建议目录和未选定框架不是阻塞依据。

### 5. 检查相关生命周期与失败路径

沿产生、持久化、传输、消费、刷新/恢复、历史数据和外部效果检查。按改动选择重要问题：

- 权限撤销、资源下架或家长解绑后，缓存、引用、下载和已生成报告是否仍可越权访问？
- 重复提交、队列重投、超时结果未知、部分失败和取消后，系统是否知道副作用有没有发生？
- 旧试卷、旧 schema、在途任务、证据更正和混合服务版本是否仍一致？
- Go、Python、网页、小程序、模型供应商和 SIS 契约变更的发布顺序是否完整？
- 应用回滚后，数据库迁移、索引、缓存、模型配置与已确认外部结果如何处理？

正确性不能只在某个可选 AI 步骤、一次实时响应或一个页面过滤器存在时成立。

### 6. 用完整责任控制改动范围

一个 PR 或一组联动改动围绕可清楚说明的行为约束。可以独立验证/回滚的无关事项通常拆开；同一跨层契约不能拆成上线期间失效的半套修复。

每处生产改动应能用同一因果链解释。新增规范、阶段文档和链接的同步修改可以构成同一完整文档交付，不以文件多寡判断质量。不得混入用户工作区中的无关文件。

### 7. 用行为证据证明结果

缺陷修复尽量提供修改前复现、修改后通过的证据，并覆盖最接近真实入口的关键反例。测试 helper 或 Mock 调用次数不能证明权限、事务、幂等、模型引用或用户最终效果。

数据库并发、约束、迁移与事务使用隔离的真实 MySQL；模型契约测试可以用受控 Mock，但引用质量和不泄题结论需要相应评测；SIS 沙箱或模拟接口不能被称为真实学校接入完成。无法自动化时记录手工步骤、证据和未验证边界。

纯文档改动验证来源一致性、迁移完整性、本地链接/锚点、状态表/接口/阶段引用和 Git 差异即可，不为了得到绿灯创建无关应用或逐字复述正文的测试。

| 资源与版本 | 未审核、退回、下架或实质修改的新版本是否被正式使用？检索索引滞后时是否重新核验？已发布题目快照是否被更新污染？ | A4、T01/T02 |

| 成绩与异步回流 | 主观初评是否经过教师确认？事务/outbox、幂等、成绩更正回放及失败重试是否保证成绩册/画像一致？SIS 失败是否独立显示并可对账？ | A6、T03/T07 |

| 网页与小程序 | 相同业务与错误语义是否一致？弱网未送达是否误显示成功？公式/题组/长文、答案披露、键盘与窄屏是否可用？ | T02/T03/T05 |

### Prompt / AI / 工具调用专项

当改动影响模型看到什么、能调用什么、服务端接受什么或失败后继续做什么时，检查以下实际链路。本文内含专项内容，不依赖其他项目未提供的 `prompt-agent-runtime.md`。

1. **上下文来源：**检索范围由服务端身份与任务确定；上传资料中的指令不得覆盖系统约束。检查拼接顺序、裁剪、历史记忆、引用、系统/用户内容边界和敏感字段最小化。
2. **任务模式与披露：**考试、练习、教师备课模式由业务状态决定。测试学生用自然语言请求切换模式、引用跳转、流式片段或工具返回获取答案时是否被服务端阻断。
3. **工具授权：**模型提出工具意图不等于授权；Go 在执行时重新验证调用主体、资源归属、参数、状态与幂等键。服务凭据不能把学生请求升级为教师审核或成绩写入。
4. **结构化结果：**拒绝缺字段、越界分值、无效标签、伪造引用和过期资源版本。解析失败、超时或候选不足时给出明确状态，不能把 fallback 包装为完整成功。
5. **副作用与恢复：**工具超时、流式取消和重试可能发生在执行前后；保存业务结果并对账，防止重复发布、确认成绩、发积分或同步 SIS。恢复不能重新推断未经保存的权威 ID。
6. **评测与可解释：**记录模型/提示版本、配置、样本、任务模式和来源。确认有效引用、无依据降级、考试禁答、L2/L1 证据与弱项推荐；质量门槛按 A1/A2/A5/A7，不仅比较文本观感。

### 文档与阶段目标专项

- 产品名使用 desk；原始来源可以保留旧名称，但不能让历史内容覆盖用户新要求。
- README 保留产品与技术基线；详细功能进入阶段目标，开发流程进入 AGENTS，工程审查方法进入本文。拆分时保留原要求并更新引用，避免多处复制后口径漂移。
- 当前阶段状态、真实目录/脚本与建议布局要分开。检查文档是否要求执行不存在的命令、链接缺失专项或使用不存在的 `dev` 分支/CI。
- 不把数学示例当作三科完成，不把 OCR/周报可选扩大为拍照/家校功能可删，也不把动态画像误改成题目难度自适应。
- 新增参数、技术建议和阶段分配标明工程属性，不降低已确认验收，也不把文档评审宣称为模型或产品测试通过。

## 重新分析的信号

下面情况应先回到因果链与责任层，不继续堆叠局部修补。这表示需要分析，不自动要求用户批准或停止全部工作。

- 根因只是复述错误现象；只改 UI 或提示词却留下服务端错误状态。
- 同一权限、资源审核或成绩确认在多个消费者重新推断。
- 新概念与旧状态相近但边界不明；上游仍产生含混数据而下游不断猜测。
- 权威身份、版本或目标来自聊天/模型、“最新值”或客户端自报。
- 测试只覆盖成功分支或实现细节，未证明关键反例和最终效果。
- 用未采纳的技术偏好、文件数量、全量清单或不存在的工具作为阻塞依据。

若因此提出阻塞，明确写出违反的行为约束、可定位证据和后果；不能只引用本清单。

## 作者提交说明

简单文档或小改动用一两段说明问题、结果与检查即可；涉及复杂行为时按相关性回答以下问题，不必填满无关字段：

```text
预期行为 / 被破坏的约束：
现象、触发条件与复现：
因果链与第一个错误决定：
权威责任模块 / 事实来源：
已检查的现有机制：
影响路径、风险与改动范围：
验证命令、结果与未验证边界：
```

涉及 schema、契约、环境、模型或部署时补充兼容、迁移/回填、发布顺序与恢复方式。重要 UI 变化提供可用的截图/录屏；样本和日志脱敏。

## 评审执行与输出

开始时确认评审对象：PR/分支/工作区、比较基线和当前提交 SHA，检查是否存在未提交改动。阅读相关上下文及调用方，不只看差异。新提交出现后，旧结论不代表新版本已通过；对受影响路径补审并注明范围。

优先报告发现，按影响排序：P0 表示应立即处理的严重故障，P1 表示高影响正确性/权限问题，P2 表示有明确触发条件的常规缺陷，P3 表示低影响问题。严重度依据真实触发条件与后果，不能只凭假设升高。风格建议与已证实缺陷分开，缺少信息时明确不确定性。

```text
评审对象：分支/PR、基线 SHA、当前 SHA；是否包含工作区改动

发现
1. [P1] 简短标题
   证据：路径:行号 → 路径:行号，触发条件或可复现步骤
   约束：原本应保证的行为及其依据
   后果：实际影响与范围
   修复方向：应回到哪个责任模块处理

验证
- 已检查/执行的路径、命令及结果
- 未验证边界、环境限制和残余风险
```

没有发现可证实问题时直说“未发现阻塞问题”，仍注明验证范围；不声称实现完成、生产安全或全部验收通过。Reviewer 无须替作者设计完整代码，但应定位到可行动的责任边界。

单独的 Review 请求默认只读；在对话中报告不等于获准向 GitHub 发 review、评论、批准或执行合并。用户同时授权修改/推送时可完成相应动作，不重复索取已有授权。相关 CI 失败、必要验证未完成或 PR 仍为 Draft 时不得宣称可合并；无 CI 时如实报告本地检查。

## 适配来源

本文保留用户提供 Review 文档的七个通用机制、行为证据和 findings-first 原则，将案例和责任边界替换为 desk 的 Go API、Python AI、教学数据和多端业务。原文依赖但未随文件提供的 Agent 专项在本文中补齐，避免留下失效链接；未引入其他项目的电商或发布流程。
